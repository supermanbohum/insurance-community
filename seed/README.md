# 보험맵 더미(Seed) 데이터 생성 스크립트

운영 시연용으로 GA 회사/지점/설계사/커뮤니티/후기/채팅/배너/방문 데이터를 실제
스키마에 맞춰 대량 생성하는 1회성 스크립트입니다. 앱 런타임 코드와는 무관하며,
`seed/` 폴더 자체를 통째로 지워도 서비스 동작에는 영향이 없습니다.

## 사전 조건

`supabase/migrations/0054_add_community_categories.sql`이 먼저 적용되어 있어야
합니다(질문/보험정보/GA이직/신입 카테고리). 적용 안 된 상태로 실행하면 스크립트가
시작 직후 에러 메시지를 출력하고 즉시 종료합니다(데이터를 절반만 만들다 마는
일은 없습니다).

## 필요한 환경변수

| 변수 | 설명 |
|---|---|
| `SUPABASE_URL` | 프로젝트의 Supabase URL (`.env.local`의 `NEXT_PUBLIC_SUPABASE_URL`과 동일한 값) |
| `SUPABASE_SERVICE_ROLE_KEY` | 서비스 롤 키 (`.env.local`의 `SUPABASE_SERVICE_ROLE_KEY`와 동일한 값) |

**주의**: 서비스 롤 키는 RLS를 완전히 우회하는 최고 권한 키입니다. 절대
커밋하거나 브라우저/클라이언트 코드에 노출하지 마세요. `seed/.env`는
`.gitignore`에 이미 포함되어 있어 실수로 커밋되지 않습니다.

설정 방법 (둘 중 하나):

1. `seed/.env.example`을 `seed/.env`로 복사한 뒤 값을 채워 넣기
2. 터미널에서 직접 export 하기

```bash
cp seed/.env.example seed/.env
# seed/.env를 열어 두 값을 채운다
```

## Node 버전

Node 18 이상 (전역 `fetch` 사용 - Storage 이미지 다운로드/Admin API 계정 조회에 필요).
추가 npm 패키지 설치는 필요 없습니다(`@supabase/supabase-js`는 이미 프로젝트
의존성으로 설치되어 있고, 스크립트 자체는 `dotenv` 없이 `.env`를 직접 파싱합니다).

## 실행 전 검증 (Dry Run)

실제로 아무것도 쓰지 않고, 이번에 실행하면 몇 건이 새로 만들어질지만 미리
확인할 수 있습니다. 조회(select)만 수행하고 insert/update/upsert/Storage
업로드/계정 생성은 단 한 번도 호출하지 않습니다.

```bash
npm run seed:dry
# 또는
node seed/_seed_tmp.mjs --dry-run
```

출력 예시(최초 실행 기준):

```
==========================
Dry Run Result (실제 DB 쓰기 없음)
==========================

GA : 50  (정보 보강 대상 - 회사 자체는 신규 생성 안 함, 총 50개 중)
지점 : 150  (사진 750장 포함, 목표 150개 중)
설계사 : 300  (신규 계정 300개 포함, 목표 300명 중)
커뮤니티 작성자 : 200  (목표 200명 중)
게시글 : 300  (목표 300개 중)
댓글 : 1000  (목표 1000개 중)
후기 : 500  (목표 500개 중)
채팅 : 200  (목표 200개 중)
배너 : 20  (목표 20개 중)

검증 소요시간 : x.x초 (조회만 수행, 쓰기 없음)
```

이미 일부를 생성한 상태에서 다시 dry-run을 돌리면, 각 줄의 숫자가 "이번에
추가로 만들어질 개수"로 자동으로 줄어듭니다(예: 재실행 시 "지점 : 0"이면
150개가 이미 다 있다는 뜻).

## 서비스 롤 키 사전 검증

Dry Run이든 실제 실행이든, 스크립트를 시작하면 가장 먼저
`SUPABASE_SERVICE_ROLE_KEY`가 실제로 유효한지 확인합니다(service_role 권한이
있어야만 성공하는 관리자 API를 한 번 호출). 키가 없거나, anon key를 잘못
넣었거나, 만료/취소된 키인 경우 아래처럼 원인과 확인 사항을 안내하고
깨끗하게 종료합니다(Node 기본 스택트레이스가 그대로 노출되는 일은 없습니다).

```
==========================
Service Role Key가 유효하지 않습니다
==========================

상세: Invalid API key
...
확인 사항:
  1) seed/.env의 SUPABASE_URL이 프로젝트 URL과 정확히 일치하는지
  2) SUPABASE_SERVICE_ROLE_KEY가 anon key가 아니라 service_role key인지
     (Supabase 대시보드 > Project Settings > API에서 확인)
  3) 키 앞뒤에 공백/줄바꿈이 섞여 들어가지 않았는지
```


또는 직접:

```bash

```

## 예상 소요시간

최초 실행(전량 신규 생성) 기준 약 5~10분. 대부분의 시간은 설계사 300명 +
커뮤니티 작성자 200명, 총 500개의 실제 Supabase Auth 계정을 생성하는
구간에서 소요됩니다(계정 8개씩 동시 처리). 재실행 시 이미 만들어진 부분은
건너뛰므로 훨씬 빠르게 끝납니다.

## 중복 실행 가능 여부 (idempotency)

**네, 여러 번 실행해도 안전합니다.** 다만 항목마다 "중복 방지"를 보장하는
방식이 다릅니다 — 데이터마다 실제 DB에 자연스러운 유니크 키가 있는 것도 있고,
없는 것도 있기 때문입니다. 정직하게 셋으로 나눠 설명합니다.

**A. DB 제약으로 완전히 보장되는 것** (상태 파일이 사라져도 안전)
- GA 회사 정보 보강: 이미 값이 있는 필드는 절대 덮어쓰지 않음(`ceo_name`/`description`이 비어있을 때만 채움).
- 지점: `ga_branch.slug`가 `{회사slug}-seed-b{1,2,3}` 형태의 결정적(deterministic) 값이고 DB에 `unique` 제약이 있어, 이미 있으면 건너뜁니다.
- 설계사/커뮤니티 작성자 계정: 이메일(`seed-planner-0001@example.invalid` 등)이 결정적 키이고, Supabase Auth 자체가 이메일 중복 가입을 막습니다. 실행 전 기존 계정을 먼저 조회해 있으면 재사용합니다.
- 북마크(즐겨찾기): `favorites`의 `(user_id, branch_id)` 유니크 제약 + `upsert(ignoreDuplicates: true)`로 처리해 중복 삽입 자체가 불가능합니다.

**B. 실행 시점의 실제 개수를 세어 부족한 만큼만 채우는 것** (DB 조회 기반, 상태 파일 불필요)
- 후기/커뮤니티 게시글, 댓글, 채팅 메시지, 방문 기록: 매번 "카테고리/테이블 전체 개수"를 먼저 세고, 목표치(후기 500개/게시글 300개/댓글 1000개/채팅 200개 등)에 못 미치는 차이만큼만 새로 만듭니다. 이미 목표를 채웠다면 0개를 만들고 넘어갑니다.
- 이 방식의 한계: 개별 게시글/댓글 내용 자체를 비교해 "이 문장은 이미 있다"고 판단하지는 않습니다. 실제 서비스에 진짜 사용자 게시글이 쌓이면 그만큼 시드 데이터가 덜 채워지는 방향으로 동작합니다(즉, 항상 안전한 쪽으로 치우쳐 있습니다 - 중복 과다 생성보다 부족 생성이 낫다는 판단).

**C. 상태 파일(`seed/.seed-state.json`)로만 판단하는 것**
- 배너: 실제 운영 배너와 시드 배너를 안전하게 구분할 방법이 없어(개수 비교가 무의미), `seed/.seed-state.json`의 `banners.done` 플래그로만 완료 여부를 판단합니다. 배너를 다시 만들고 싶다면 이 파일에서 `banners` 항목을 지우고 재실행하세요.

`seed/.seed-state.json`은 스크립트가 자동 생성/갱신하며 `.gitignore`에 포함되어
커밋되지 않습니다. 지워도 A/B 항목은 DB 조회로 스스로 복구되고, C(배너)만
다시 생성됩니다.

## 실패 시 복구 방법

스크립트는 각 단계를 순서대로 처리하며, 도중에 네트워크 오류 등으로 중단돼도
그 시점까지 만든 데이터는 DB에 그대로 남아 있습니다. **가장 간단한 복구
방법은 그냥 다시 실행하는 것입니다** (`npm run seed`) — 위 idempotency 규칙에
따라 이미 만든 부분은 건너뛰고 나머지만 이어서 만듭니다.

그 외 상황별 대처:

- **"카테고리가 없습니다" 에러로 즉시 종료**: `supabase/migrations/0054_add_community_categories.sql`을 Supabase SQL 편집기에서 먼저 실행하세요.
- **`SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` 관련 에러로 즉시 종료**: `seed/.env` 값을 확인하세요.
- **콘솔에 개별 `insert error`가 몇 건 섞여 있지만 스크립트는 끝까지 실행됨**: 정상적인 부분 실패 허용 설계입니다. 그 항목만 목표치에 못 미치게 되는데, 다시 실행하면 부족한 만큼 자동으로 채워집니다.
- **완전히 초기화하고 처음부터 다시 만들고 싶은 경우**: 이 스크립트는 되돌리기(삭제) 기능은 제공하지 않습니다. `seed-planner-%`/`seed-author-%` 이메일 패턴, `{회사slug}-seed-b%` 지점 slug 패턴으로 만든 행을 식별할 수 있으니, 필요하다면 별도로 삭제 SQL을 작성해 정리한 뒤 재실행하세요.

## 스키마 제약으로 조정한 부분 (참고)

요청 스펙 중 아래 항목은 실제 DB 스키마에 저장 컬럼이 없어 만들지 않았습니다
(허위로 다른 컬럼에 끼워 넣지 않기 위한 선택입니다):

- GA 회사 단위 조회수/좋아요/창립년도, 지점 좋아요, 설계사 좋아요/후기수, 댓글 조회수
- 검색 자동완성/홈 인기·최근 리스트/지도 마커/관리자 통계는 전용 테이블이 없고
  전부 회사/지점/설계사 실데이터에서 실시간 계산되므로 별도로 만들지 않아도
  이 스크립트가 채우는 기본 데이터만으로 자동으로 채워집니다.
- `ga_company.logo_path`/`planner_profiles.profile_photo_path`는 Supabase Storage
  경로 전용이라 외부 URL을 쓸 수 없습니다. 비워두며, 기존 UI의 그라디언트+아이콘
  fallback으로 자연스럽게 표시됩니다. 지점 사진(`branch_media`)은 외부 URL을
  지원해 Picsum 링크를 그대로 씁니다. 배너 이미지는 실제로 `banner-images`
  Storage 버킷에 업로드합니다.
